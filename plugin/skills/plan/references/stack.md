# Shared stack config: `stack.json`

Nobody writes this file directly. Change any field with `koppler stack set <path> <value>` or `koppler stack unset <path>` (read one with `koppler stack get <path>`); paths look like `apps.orders.url`, `apps.orders.prereqs[0].port` or `apps.orders.envs.prod.start`. Each change is checked against the rules below before it is kept.
A field the format does not know is refused (`koppler stack schema` lists every one); anything else worth knowing goes in the stack's `notes`.
`koppler stack check` reports each one an older stack still holds, with what replaced it (`run` by `start`, `note` and `config` by `description` or `notes`).
Take it out with `koppler stack unset <path>`.

One file per stack, in the team's repo, reviewed through PRs.
It holds facts about the apps, never secret values.
`koppler sync` validates it (`envs`, and `name` / `kind` / `slug` per app, `consumes` pointing at known apps) and copies it to `<state>/registry.json`.

```json
{
  "name": "Orders",
  "envs": ["qa", "prod"],
  "notes": [
    "Stack-wide facts the agent reads first, e.g. which tunnel can move to another port."
  ],
  "checks": [
    {
      "name": "nuget-feed",
      "kinds": ["dotnet"],
      "run": "dotnet nuget list source | grep -q acme",
      "ok": "feed configured",
      "fix": "see the README setup"
    }
  ],
  "apps": {
    "orders-api": {
      "name": "Orders API",
      "kind": "dotnet",
      "slug": "acme/orders-api",
      "project": "src/Orders.Api",
      "launchSettings": "src/Orders.Api/Properties/launchSettings.json",
      "baseProfile": "QA",
      "url": "http://localhost:5001",
      "deployedUrl": "https://orders.qa.acme.dev",
      "consumes": {
        "payments-api": {
          "how": "env",
          "env": ["Payments__BaseUrl"],
          "deployed": "https://payments.qa.acme.dev"
        }
      },
      "prereqs": [
        { "sso": "acme-qa", "note": "AWS login for config and secrets" },
        {
          "tunnel": "db-qa.internal.acme.dev",
          "port": 5432,
          "cmd": "cloudflared access tcp --hostname db-qa.internal.acme.dev --url localhost:5432"
        }
      ],
      "secrets": [
        {
          "env": "ConnectionStrings__DB",
          "when": "always",
          "fetch": {
            "cli": "<command> | koppler secret set orders-api ConnectionStrings__DB --stdin",
            "ui": "<where to copy it from>"
          }
        }
      ],
      "envs": {
        "prod": {
          "baseProfile": "PROD",
          "deployedUrl": "https://orders.acme.dev"
        }
      }
    }
  }
}
```

| `checks`                                 | The stack's own health checks, run when it loads (`koppler doctor`). | `apps.<id>.outside`                      | The app does not run on this Mac, or has nothing to run, with a short why. It is never planned, sent or started (`koppler up` refuses it by name), and needs no `slug`. Its card shows the address its `deployedUrl` gives for the board's environment (the Salesforce sandbox on QA, production on PROD). `koppler discover --deployed` drafts known ones (Salesforce) from each app's addresses per environment, with the calls to them (`outsideSuggestions`). A job is always the deployed one. It is never planned, sent or started (`koppler up` refuses it by name), and has no card on a run board. It shows in Discover beside the app whose repo it ships from, with its calls. Draft it from an EventBridge rule with an ECS or Lambda target, or a SAM `Type: Schedule` event.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |

Optional, one line; shown on its exported card (an outside service's card still says so), in Discover's panel and in `koppler guide`. Write it from the repo's README, never from guesses, and set it with `koppler stack set`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

A view only: runs, environments and secrets stay the same. | `apps.<id>.areas`                        | The areas the app belongs to, by id: `["payments", "shipping"]`. With none, it shows in every area. | `presets[n].area`                        | A team board's area set by hand, by id. Without it, the board is in the area most of its apps are in. Only apps with one count, and a tie goes to the smaller area. `koppler use --boards` lists each board with its area, `--area <id>` keeps one. Set a team board's with `koppler stack set presets[<n>].area <id>`; `koppler board edit "<name>" --area <id>\|auto` sets your own board's (on a team board it makes your own copy).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `queues`                                 | Top-level: `{ "<id>": { "name", "type", "queue"? } }`, the queues, topics and event buses between apps. `type` is `sqs`, `sns`, `eventbridge`, `kafka` or `other`. `queue` is its real name (default the id), per environment under `envs.<env>.queue`. `feeds` names the queues, topics and buses it hands its messages to, and how: `{ "<queue>": { "via": "pipe" \| "rule" \| "subscription" } }`. Examples: a Kafka topic piped onto an event bus, a bus whose rule forwards to another bus, an SNS topic with an SQS subscription.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `databases`                              | Top-level: `{ "<id>": { "name", "kind", "tunnel"?, "port"?, "cmd"?, "hosts"?, "envs"?: { "<env>": { "tunnel", "port", "cmd", "hosts" } } } }`, each database or cache the apps use, named once. `kind` is `postgres`, `mysql`, `valkey` or another word. `tunnel` and `port` say how this Mac reaches it on the first environment. `hosts` says the name the apps' own connection settings dial, pointed at the tunnel. Another environment states its own under `envs`, never borrowing the first one's. An app that `uses` it gets that tunnel and hosts entry as its own needs.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `resources`                              | Top-level: `{ "<id>": { "type", "name", ... } }`, what the apps use that is deployed only and never runs here, shown on Discover and never on a board. `type` is `s3`, `apigw` or `sfn`. An `s3` is a bucket: `bucket`, and `envs.<env>.bucket` for another environment's. An `apigw` is an API Gateway: `routes`, `{ "POST /orders": "<app id>" }` or `"queue:<id>"`, what each route hands to. An `sfn` is a Step Functions state machine: `startedBy`, the app ids that start it, and `steps`, `[{ "name", "calls"?: "<app id>" }]` in order.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `apps.<id>.buckets.<resource>`           | The S3 buckets the app uses, by id under `resources`: `{ "access": "read" \| "write" \| "both" }`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `apps.<id>.publishes`, `apps.<id>.reads` | `koppler discover --deployed` drafts them, with `queues`, from the Terraform (who sends and reads, the settings carrying each address, what feeds a queue from outside). Confirm before adding. The queues the app sends to or takes from: `{ "<queue>": { "env"?: [settings holding the queue's URL] } }`. On the canvas an app is off its queues until its card's Queues switch is on (`queues: true` in a preset). Then they draw a queue card between its apps, with a Local switch. Switched on, `koppler up` runs it locally. SQS: one AWS emulator in Docker on port 4566 holds the queue. Every app on it starts with `AWS_ENDPOINT_URL_SQS` (which current AWS SDKs read) and its `env` settings pointed at the local queue. Kafka: one broker in Docker (`apache/kafka`) on `localhost:9092` gets the topic (`queue`). Every app on it starts with its `env` settings (its broker list, e.g. `Kafka__BootstrapServers`) set to `localhost:9092`. A broker setup that needs sign-in (SASL, MSK IAM) has to be turned off for the local run, e.g. by a remembered change. SNS and EventBridge stay deployed. Off, a local reader takes messages off the deployed queue, so the deployed reader misses those; the card says so. A read entry can say how the app reads it when not by itself: `{ "via": "rule to Lambda" }`. That covers a pipe or rule to a Lambda or an API destination. The canvas shows it on the link. A local app read that way takes nothing off the deployed queue. |

Which programs are needed is worked out from the stack itself: each app kind's own, and the first word of every prerequisite's `cmd`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

Local libraries need nothing in `stack.json`.
`koppler sync` matches each app's dependencies (`pubspec.yaml`, `package.json`) with the packages your clones publish.
The card offers a Libraries switch for each.
Switched on, `koppler up` points the app at your clone (a `pubspec_overrides.yaml` for Dart, `npm install --no-save` for npm).
Stop reverts it.
.NET libraries are not covered yet.

Top-level `presets` are the team boards: `[{ "name": "Mobile App + Mobile API", "version": 1, "nodes": { "<app>": { "run": "cli", "platform"?, "branch"?, "note"? } }, "edges": [{ "from", "to" }] }]`. The canvas lays them out by who calls whom; `koppler sync` checks every app and cable exists. Every board a user builds is kept as their own, saved as they change it; Share copies it as JSON to add here.
A single preset in its own `.json` file, a list of them, or a whole `stack.json` can be opened from the canvas's board selector.
Each can be opened as a file or as a GitHub link.
That preset file is the JSON that Copy in the board selector copies.
Share makes a board a team board of the stack.

Every preset carries the `version` of the preset format it was saved in (`VERSION` in `core/presets`, currently 1); `koppler sync` requires it on shared presets.
Before any preset opens, its version is compared with the one this Koppler reads:

- older: it is brought up to date one step at a time.
  `MIGRATIONS[n]` turns version n into n + 1; a file without a version is read as version 0;
- newer: it is refused, with a message to update Koppler.

It is then checked against the stack and your clones:

- apps the stack does not have or you have not cloned are left out;
- a run mode or platform the app does not offer falls back to one it does;
- a cable between apps that do not call each other is dropped;
- a branch missing from your clone is pointed out.

Each change is listed when the preset loads; a preset with nothing left to open is refused and the board stays as it was.
To change the format: raise `VERSION`, add the `MIGRATIONS` step from the previous version, and cover it in `app/src/core/presets.test.ts`.

The format has no free-form fields: anything else worth knowing goes in the app's `description`, a prerequisite's `note`, or the stack's `notes`.

## Expressions

A value can name another app's fact instead of repeating it: `"url": "http://localhost:{{orders-api.port}}"`, `"local": "http://{{orders-api.host}}:{{orders-api.port}}/v1"`.
`{{<app>.<field>}}` is any field of that app (its top-level value), and `port` and `host` also come from its `url`.
A value that is only an expression keeps the type of what it names, so `"port": "{{db-api.dbPort}}"` is a number.
`stack.json` keeps the expressions, and Settings shows and saves them as written; Koppler fills them in where it uses the stack (runs, the board, checks).
One that names nothing, or only itself, is a problem `koppler stack check` reports, and the stack is not saved with it.

## What the repos say

Right after repos are added on the canvas, Koppler reads the clones.
It does so again later from "Look through the repos again" in the stack menu (`koppler discover [--apply]`).
Then it offers, for the user to tick:

- where each app runs locally (launch settings, `.env`, the framework's default port), as its `url`;
- each app's deployed address per environment, from its Terraform, as `deployedUrl` (and `envs.<env>.deployedUrl`);
- an environment the repos name differently (QA deployed as `dev`), as `envAliases`, with the addresses that follow from it;
- who calls whom: another app's address in a caller's code, as `consumes.<callee>` with `how: unknown` and where it was found.
  Only ticked findings are written; the agent works out `how` the first time that cable is used.

## Shared stacks from GitHub

A stack can be used straight from a link to its `stack.json` on GitHub, with no clone.
Use `koppler link <url>`, or "Use" next to the link field on the canvas.
Koppler reads it through the user's `gh` login and keeps a copy in `~/.config/koppler/stacks/<owner>-<repo>-<name>/`, with `.source.json` holding the link and the file as last fetched.

- What Koppler learns goes into the copy and shows as "Changes not shared yet" in the stack menu (`koppler link`).
- "Check for updates" (`koppler link update`) brings in GitHub's changes; when both sides changed it refuses rather than lose either.
- "Open pull request" (`koppler link pr`) pushes a branch `koppler/<stack>-<id>` with the copy and opens a pull request listing the changes, after the user confirms. Once it is merged, the next update finds the two in line.
- "Discard my changes" (`koppler link discard`) puts the copy back to the shared file as last fetched.

It gets the settings it reads, named in `"env": ["MESSAGES_API_BASE_URL", "MESSAGES_API_KEY"]`, from what Koppler sets.

The port in the app's `url` wins over the usual one. The recipes live in the app's `core/kinds`; only .NET, Flutter, Node and the web frameworks have been run for real so far.

## Adding apps

Apps join the stack through the repo picker on the canvas.
Open it with `koppler init --pick` (it opens by itself on a stack with no apps) or "Add repos" above the Apps list.
It lists the clones found on this machine by folder.
Each shows the kind it looks like (.NET, Flutter, Node, web; ask when it cannot tell).
Each also gets a name taken from the repo, which can be edited.
Only the ticked ones are written to `stack.json`, as `{ name, kind, slug, pending }`: listed, but not set up yet. Their run facts are collected the first time they are used.

## Who calls whom

Map every app's outgoing calls, not just the app you started from: a missing or empty `consumes` means "not mapped yet", never "calls nothing".
`koppler sync` helps: it searches each cloned app's repo for the other apps' deployed hosts (`deployedUrl`, and each `consumes.<app>.deployed`) and prints:

- `FOUND a -> b`: a call in `a`'s repo that `stack.json` does not list. The canvas lets you cable it; confirm how a local run repoints it, then add it with `koppler stack set apps.<a>.consumes.<b> '{...}'`.
- `UNKNOWN app`: no deployed address is known for it, so calls to it cannot be found. Add its `deployedUrl`.
- `SHARED host`: two apps use the same address (e.g. one app's QA URL pointing at another app), so calls to it are not attributed. Check those by hand.

Tests, docs, lock files and migration tools are not searched.

## Drafting from Terraform

`koppler discover --deployed [app...]` reads the Terraform in each clone (no cloud access) and drafts, per environment:

- the app's deployed address (API Gateway domain, CDN alias or DNS record), marked `NEW`, `matches stack.json` or `OTHER than stack.json`;
- the names of its settings, and which of them hold or point to a secret;
- Secrets Manager secret names and Parameter Store paths;
- calls: a setting whose address belongs to another app;
- queues, topics and event buses, and what feeds what (`queueSuggestions`).
  These are SQS queues and SNS topics, and EventBridge buses (`aws_cloudwatch_event_bus`).
  Also Kafka topics a pipe reads (`topic_name` of an `aws_pipes_pipe` or `awscc_pipes_pipe`, one per topic of a list).
  Also pipes (source to target), and rules with their targets (a bus to a queue, a Lambda, or another account's bus by its ARN).
  Also SNS subscriptions (`aws_sns_topic_subscription`).
  A queue read through a pipe or rule to a Lambda or an API destination is drafted as `reads` with `via`, such as `"rule to Lambda"`.
  Feeds of queues the stack already has are under `queueSuggestions.feeds`.
  Topic names in a map (`for_each = var.kafka.topics`, `each.value`), in a `.tfvars.json`, or in the variables of the folder above a module are read too.
- buckets, API Gateways and Step Functions (`resourceSuggestions`), for `resources` and each app's `buckets`.
  An S3 bucket an app's own policies read or write (`s3:Get*`/`s3:List*`, `s3:Put*`/`s3:Delete*`), declared in its clone or named by its ARN.
  It comes with the environments' bucket names.
  An API Gateway (v2) only when a route hands to more than the app's own Lambda, such as a queue.
  Each state machine's steps from its `jsonencode` definition, in order from `StartAt`.
  It has `calls` on a step that runs the app's own Lambda, and `startedBy` when the app's policies may start it.
  It has a note when a schedule does.
  Record them with `koppler stack set` after checking them, as with queues.

`koppler discover --deployed --aws [--env <env>]` then checks what AWS runs between the queues.
It uses each app's AWS profile for that environment (its `-view` twin when the AWS config has one).
It only lists and describes EventBridge Pipes and Lambda event source mappings, never a value or a message.
Each line is `OK`, `FOUND` (in AWS, not in the stack) or `MISSING` (in the stack, not in AWS).
A profile that is not signed in is named with its `aws sso login` command.

It reads out names and plain addresses only (a host, or an http(s) URL with no credentials or query).
Every other value stays in the repo.
Environments come from variable files named after them (`deployment-dev.tfvars`) or, without those, from trying each stack environment and alias as the Terraform workspace.
What it cannot work out is reported as not found or counted.
Examples are a domain passed in by the deploy pipeline, or a name built from a random suffix.
The draft, with a `suggestions` block shaped like `stack.json`, goes to `<state>/stack.deployed.json`. Review it, then keep what holds with `koppler discover --apply` or `koppler stack set`.

## Sign-ins that are not AWS

`sso` is shorthand for an AWS profile.
Add `account` (the 12-digit id) next to it when the profile must be one account.
Signed in to another one then counts as not signed in, and nothing starts.
A profile with an `sso_session` can still make an app on an older AWS SDK ask for its own browser sign-in.
`koppler doctor` and `koppler up` say so beforehand.
While the app waits, `koppler up` prints the page and code to approve and shows them on its card.
Pass them on to the user.
A declared sign-in does the same inside its own `check` command.
Any other sign-in (Azure, Google Cloud, Firebase, a company tool) is declared once at the top of the stack.
The apps that need it name it:

```json
"signIns": {
  "acme-dev": {
    "what": "Azure",
    "check": "az account get-access-token --tenant acme",
    "login": "az login --tenant acme",
    "env": { "AZURE_TENANT_ID": "acme" }
  }
},
"apps": { "orders": { "prereqs": [{ "signIn": "acme-dev" }] } }
```

- `check` succeeds while the sign-in holds. Koppler runs it before a run starts anything, and it is a command of the stack, so it runs only after `koppler doctor --approve`.
- `login` is what the user runs to sign in. Koppler shows it and never runs it.
- `env` is given to the app when Koppler starts it.
- Like `sso`, a sign-in belongs to one environment: each environment that needs one lists its own.
